# Aid Protocol - EVM Contract Security Audit

- **Contracts:** `AidEscrowFactory` (`chain/evm/src/AidEscrowFactory.sol`), `CampaignEscrow` (`chain/evm/src/CampaignEscrow.sol`), `TestToken` (`chain/evm/src/TestToken.sol`)
- **Compiler:** Solidity `^0.8.26` (checked arithmetic on by default)
- **Auditor:** Mira (EVM/Solidity security review)
- **Date:** 2026-06-30
- **Commit basis:** working tree at audit time (not a tagged release)

## Scope

Full manual adversarial review of the three in-scope EVM contracts. Reviewed: the factory's role keys and token allowlist, per-campaign escrow isolation, native ETH and ERC-20 donation/release/refund accounting, the proof-gated tranche release, pull-based pro-rata refunds, the freeze and refund (redirect) controls, reentrancy on every external call (ETH `call` and ERC-20 `call`), checks-effects-interactions ordering, integer arithmetic, low-level-call safety, and the approver-vs-authority separation of duties. The Foundry suite (`chain/evm/test/AidEscrow.t.sol`) was read to confirm intended behavior. Contract code was not modified.

This review explicitly cross-checks the four issues confirmed and remediated on the Solana side (`audit/audit-solana-2026-06-30.md`): (1) allowlist admin-gating, (2) release bounded by funds raised, (3) approver != authority enforcement, (4) admin/owner as a rotatable Safe-compatible role. EVM analogue status is called out per finding and summarized at the end.

`TestToken` is explicitly testnet-only (open faucet `mint`) and is not a protocol-trust component; it is noted but not treated as a production risk.

**Tooling note.** This manual review is the deliverable. The automated Slither + Aderyn pass should be run in Docker (`chain/docker/`, Foundry stable) as a follow-up and required to produce zero new findings before any deploy, per the project's hard rules. Those tools were NOT run as part of this report.

Out of scope: the Solana program, the Worker / D1 read model, the client, and the build toolchain.

## Detailed findings

### 1. Critical - Release is not bounded by funds actually raised; `approved` has no `raised` ceiling

**Location:** `CampaignEscrow._checkRelease`, `recordProof`, `releaseNative`, `releaseToken`.

**Description.** Release is gated solely by the approver-committed per-tranche ceiling:

```solidity
function _checkRelease(uint256 tranche, address asset, uint256 amount) internal view {
    if (proofHash[tranche] == bytes32(0)) revert NotApproved();
    if (releasedForTranche[tranche][asset] + amount > approved[tranche][asset]) revert ExceedsApproved();
}
```

Nothing ties `approved[tranche][asset]` (or cumulative `releasedNative` / `releasedToken[token]`) to `raisedNative` / `raisedToken[token]`. `recordProof` accumulates `approved[tranche][asset] += amount` with no relationship to funds raised, across an unbounded set of `tranche` values (see findings 3 and 8). The authority can then release up to that approver-set figure regardless of what donors actually contributed.

**Exploit path.** A faulty or compromised approver records `approved` for tranches 0,1,2,... whose total exceeds `raisedNative`. The authority calls `releaseNative` repeatedly. For ETH the contract custody is `raisedNative - releasedNative` (plus any forced ETH, finding 9), so a release beyond on-hand ETH reverts on the `to.call{value:}` low-level send and is not directly a theft of donor principal in the simple case. The real damage is twofold:

1. `releasedNative` (a pure accounting counter incremented BEFORE the send) can be advanced past `raisedNative` whenever the contract holds any extra ETH (finding 9), or `releasedForTranche`/`releasedToken` can be inflated; this directly enables the refund DoS in finding 2.
2. For tokens, `releaseToken` moves `amount` out of the shared escrow token balance with no `released <= raised` ceiling. Because the escrow's token balance is exactly the sum of donations for that token (per-campaign isolation holds), over-release simply drains the entire token balance to the authority-chosen recipient, leaving nothing for the pro-rata refund pool that `enableRefunds` promises donors. The approved-amount ceiling is the ONLY guard, and it is set by a single role with no `raised` anchor.

This is the direct EVM analogue of Solana audit finding #2 ("Release is not bounded by funds actually raised") combined with finding #4 ("unbounded approved accumulation across arbitrary tranches"). On Solana those were graded Critical/High and fixed by adding `released + amount <= raised` and a cumulative `total_approved <= raised` invariant. The EVM contract has neither check.

**Remediation.** Add a funds-on-hand ceiling independent of the approval, per asset:

- In `releaseNative`: `require(releasedNative + amount <= raisedNative, ExceedsRaised)`.
- In `releaseToken`: `require(releasedToken[token] + amount <= raisedToken[token], ExceedsRaised)`.
- In `recordProof`: track cumulative approved per asset and require `totalApproved[asset] + amount <= raised(asset)` so the ceiling itself can never exceed raised.

Keep these as belt-and-suspenders alongside the existing `approved` check.

### 2. High - Over-release bricks refunds via checked-subtraction underflow (donor-funds DoS)

**Location:** `CampaignEscrow._refundable` (called from `refundNative`, `refundToken`).

**Description.** `_refundable` computes the undisbursed remainder with an unchecked-by-intent subtraction that is actually checked under Solidity 0.8:

```solidity
function _refundable(uint256 contributed, uint256 raised, uint256 released) internal pure returns (uint256) {
    if (raised == 0) return 0;
    uint256 remaining = raised - released;   // reverts if released > raised
    return (contributed * remaining) / raised;
}
```

If `released > raised` for an asset (reachable via finding 1, where the approver over-approves and the authority over-advances the `released*` counters, or via forced ETH in finding 9), then `raised - released` underflows and reverts. Because `refundNative` / `refundToken` both route through `_refundable`, EVERY donor's refund call reverts. Refunds are the protocol's promised remedy on fraud; this turns a release-accounting error into a permanent, un-recoverable denial of donor refunds, with no admin path to repair the counters.

**Exploit path.** (Chains with finding 1.) Approver over-approves; authority releases beyond `raised` for some asset (possible for tokens directly, or for native when the contract holds forced ETH). `releasedNative`/`releasedToken[token]` now exceed the corresponding `raised`. Authority calls `enableRefunds`. Every `refundNative` / `refundToken(token)` reverts on the underflow. Honest donors are permanently unable to reclaim funds.

This mirrors the DoS noted in Solana finding #2 ("`refundable()` computes `raised - released` and underflows ... refunds become impossible for honest donors").

**Remediation.** Fix the root cause (finding 1) so `released` can never exceed `raised`. As defense in depth, make `_refundable` saturating: `uint256 remaining = released >= raised ? 0 : raised - released;` so a corrupted counter cannot brick the whole refund path.

### 3. High - `approved` ceiling is re-openable: `recordProof` accumulates and overwrites the proof hash

**Location:** `CampaignEscrow.recordProof`.

**Description.**

```solidity
function recordProof(uint256 tranche, bytes32 hash, address asset, uint256 amount) external onlyApprover {
    if (hash == bytes32(0)) revert NotApproved();
    proofHash[tranche] = hash;              // overwritten on every call, no history
    approved[tranche][asset] += amount;     // accumulates; never reset against released
    emit ProofRecorded(tranche, hash, asset, amount);
}
```

The per-tranche approved amount is a mutable, re-openable accumulator, and the proof hash is overwritten with no record of the prior commitment. After the authority releases the full `approved` for a tranche, the approver can call `recordProof` again with a fresh hash and a new `amount`, raising the headroom (`approved - releasedForTranche`) and unlocking another release against the same tranche, decoupled from any single proof. The on-chain "approved per tranche per asset" is therefore not an immutable commitment.

This is the EVM analogue of Solana finding #5 (`init_if_needed` on `Approval` permitting ceiling reuse) and the accumulation half of Solana finding #4. On Solana the fix was `init` (write-once) plus a monotonic tranche counter.

**Exploit path.** Approver records `approved[0][NATIVE] = 4 ether`; authority releases 4. Approver calls `recordProof(0, newHash, NATIVE, 4 ether)` again; `approved[0][NATIVE]` is now 8, headroom is 4, and the authority releases another 4 against the same tranche with no new donor funds and no immutable proof binding. Amplifies finding 1.

**Remediation.** Make each `(tranche, asset)` proof write-once: revert if `approved[tranche][asset] != 0` (or if `proofHash[tranche] != 0`) on re-record. If multiple proofs per tranche are legitimately needed, key them by an explicit proof index and treat each as write-once. Combine with the `raised` ceiling from finding 1.

### 4. Medium - Token release/refund accounting trusts the `amount` argument, not the measured balance delta

**Location:** `CampaignEscrow.donateToken`, `releaseToken`, `refundToken`.

**Description.** `donateToken` credits the recorded books from the call argument before/around the transfer, not from the actual balance received:

```solidity
raisedToken[token] += amount;
donorToken[msg.sender][token] += amount;
emit DonationToken(msg.sender, token, amount, isAnonymous);
_safeTransferFrom(token, msg.sender, address(this), amount);
```

For a fee-on-transfer or rebasing/non-standard ERC-20, the escrow receives less than `amount`, but `raisedToken` records the full `amount`. Releases and refunds then move the recorded figures out of a token balance that is short, so the last claimants' transfers revert (the escrow runs dry), or release drains more than was truly received. Per-campaign isolation means this cannot reach OTHER campaigns' funds (each escrow is its own contract), but within a campaign the books desync from custody.

The reachable risk is bounded by the allowlist: only `authority`-approved tokens can be donated (`isAllowed` gate), and the intended set is USDC/USDT (no fee on transfer today). So this is latent, not currently exploitable, PROVIDED the allowlist is never used to admit a fee-bearing or deflationary token. It becomes a live loss vector the moment such a token is registered. This is the EVM analogue of Solana finding #6 (no escrow-balance reconciliation), which was mitigated there by closing the admission path and documenting classic-token-only.

**Remediation.** Use delta-aware accounting in `donateToken`: read `IERC20(token).balanceOf(address(this))` before and after `_safeTransferFrom` and credit the measured delta to `raisedToken`/`donorToken`. Keep the allowlist strictly to non-fee standard tokens and document the constraint. This also hardens release/refund, which then operate on truthful `raised` figures.

### 5. Medium - Single key can hold both roles (separation-of-duties is opt-in and authority-revocable)

**Location:** `AidEscrowFactory` constructor and `setApprover`.

**Description.** The hard rule in AGENTS.md is "never let one key do both." The factory both defaults to and permits exactly that:

```solidity
constructor(address _authority) {
    ...
    authority = _authority;
    approver = _authority; // default; set a distinct approver for separation of duties
}

function setApprover(address newApprover) external onlyAuthority {
    if (newApprover == address(0)) revert ZeroAddress();
    ...
    approver = newApprover;   // no check that newApprover != authority
}
```

A freshly deployed factory has `approver == authority`, so every escrow it creates lets one key call both `recordProof` and `release` until someone remembers to call `setApprover`. Even after separation, `setAuthority` can later set `authority = approver`, or `setApprover` can set `approver = authority`, collapsing dual control at will. Because escrows read both roles live from the factory, this instantly defeats separation across ALL campaigns and directly amplifies findings 1 and 3 (one key can both over-approve and release).

This is the EVM analogue of Solana finding #10 (`set_approver` collapsing separation of duties; `approver = authority` default), which was re-graded High and fixed by forbidding `approver == authority` at init and in the setter.

**Remediation.** Enforce `approver != authority` in `setApprover` AND in `setAuthority` (reject a new authority equal to the current approver), and require an explicit distinct `_approver` constructor argument instead of defaulting `approver = authority`. Optionally gate `releaseNative`/`releaseToken` on `IAidFactory(factory).approver() != IAidFactory(factory).authority()`.

### 6. Medium - No two-step ownership transfer; `setAuthority` can brick the protocol in one call

**Location:** `AidEscrowFactory.setAuthority`, `setApprover`.

**Description.** `setAuthority` is a single-step transfer guarded only by `onlyAuthority` and a zero-address check:

```solidity
function setAuthority(address newAuthority) external onlyAuthority {
    if (newAuthority == address(0)) revert ZeroAddress();
    emit AuthorityChanged(authority, newAuthority);
    authority = newAuthority;
}
```

A typo or a mis-set address (an EOA with a lost key, a non-Safe contract that cannot call the factory, or a wrong chain's Safe) immediately and irrevocably transfers control. Since the authority is the ONLY role that can create campaigns, register tokens, release, freeze, enable refunds, and rotate roles, a bad `setAuthority` bricks the entire protocol with no recovery. The same applies to `setApprover` (a wrong approver halts proof recording, though that is less catastrophic). The contract is otherwise Safe-compatible (the role is a plain `address`, so a Safe multisig can hold it, satisfying the design intent in the factory NatSpec), but there is no acceptance handshake.

This is the EVM mirror of the Solana `set_admin` work: on EVM the rotatable, Safe-compatible role already exists as `authority`/`approver`, but it lacks the safety of a two-step claim.

**Remediation.** Adopt a two-step (propose / accept) transfer for both `authority` and `approver` (e.g. OpenZeppelin `Ownable2Step` semantics, or a hand-rolled `pendingAuthority` + `acceptAuthority`). The new holder must call `accept*` from the new key, proving control before the rotation takes effect. This is exactly the Safe-compatible, rotatable-role hardening called for in the improvement list.

### 7. Low - Authority-chosen release `to` allows self-/escrow-directed transfers that burn approved headroom

**Location:** `CampaignEscrow.releaseNative`, `releaseToken`.

**Description.** `to` is fully authority-chosen and only checked for the zero address. Setting `to = address(this)` on `releaseToken` (or any address the authority controls) sends tokens back into the escrow while still advancing `releasedForTranche` and `releasedToken[token]`. This burns approved headroom and inflates the released counters without disbursing to a beneficiary, corrupting the released accounting and the audit trail, and (combined with finding 1/2) can push `releasedToken` toward/past `raisedToken`. No direct external theft, but it muddies accounting and the refund denominator. This parallels Solana finding #9 (authority-chosen recipient self-transfer).

**Remediation.** Reject `to == address(this)` in both release functions. Consider binding the recipient to a value committed in the proof so the authority cannot freely redirect.

### 8. Low - `recordProof` accepts `amount == 0` and arbitrary unbounded `tranche`

**Location:** `CampaignEscrow.recordProof`.

**Description.** `recordProof` validates only that `hash != 0`. It accepts `amount == 0` (a no-op proof that still overwrites `proofHash[tranche]`, see finding 3) and any `uint256 tranche` with no ordering or monotonic counter, so tranches can be sprayed across the full key space with no aggregate ceiling. Combined with finding 1, this is what makes "unbounded approved across arbitrary tranches" reachable. Mirrors the Solana finding #4 sub-issues (reject `amount == 0`, validate tranche against a monotonic counter).

**Remediation.** Reject `amount == 0` (`ZeroAmount`). Track a per-campaign monotonic next-tranche counter and require `tranche <= nextTranche` so tranche indices are sequential.

### 9. Low - Forced ETH is releasable and not refundable; refund dust is stranded

**Location:** `CampaignEscrow.releaseNative`, `_refundable`.

**Description.** Two related accounting gaps:

1. The escrow has no `receive()`/`fallback()`, so normal sends revert, but ETH can still be forced in via `selfdestruct` of another contract or as a pre-computed-address pre-deposit. Forced ETH is not counted in `raisedNative` and has no donor, yet `releaseNative` sends from the raw contract balance, so forced ETH is releasable by the authority (within the approval ceiling) and is never refundable to anyone. It also enables `releasedNative` to exceed `raisedNative` (feeding findings 1 and 2).
2. `_refundable` truncates `(contributed * remaining) / raised` toward zero per donor, so the sum of refunds is `<= remaining`, leaving a few wei/atoms of dust permanently locked with no sweep path. This matches Solana finding #11 (refund truncation locks dust, Informational there).

**Remediation.** Track releasable native funds as `raisedNative - releasedNative` and require `releasedNative + amount <= raisedNative` in `releaseNative` (this is the finding-1 fix and also neutralizes forced ETH for release). Optionally add an authority sweep of residual dust to a treasury after refunds settle, or assign the remainder to the final claimant.

### 10. Informational - `unregisterToken` does not reject the zero address

**Location:** `AidEscrowFactory.unregisterToken`.

**Description.** `registerToken` rejects `token == address(0)`, but `unregisterToken` does not. Setting/clearing the zero-address entry is harmless (the zero token is never donatable), but the asymmetry is a minor code-quality inconsistency that a linter (Slither/Aderyn) will likely flag.

**Remediation.** Either add the same `ZeroAddress` guard for symmetry or document that it is intentionally permissive.

### 11. Informational - Committed proof hash is never bound to amount/recipient or verified on-chain

**Location:** `CampaignEscrow.recordProof`, `_checkRelease`.

**Description.** `recordProof` commits `hash` (rejecting only the all-zero sentinel), and `_checkRelease` only verifies `proofHash[tranche] != 0`. The content the hash represents is never verified on-chain, and the hash is not bound to the released `amount`, `asset`, or `to`. The hash is a pure off-chain attestation, overwritten on re-record (finding 3). This is by design (it mirrors Solana finding #12, "committed proof hash is never verified or bound", documented as by-design there), but reviewers should not read the on-chain presence check as proof verification.

**Remediation.** Document that the hash is an off-chain commitment only. If stronger guarantees are wanted, bind the hash to `(amount, asset, tranche, to)` and make it write-once (which finding 3's fix already provides for the ceiling).

## Reentrancy and checks-effects-interactions note

All three external-call sites were reviewed for reentrancy:

- `releaseNative` (`to.call{value:}`), `releaseToken` / `donateToken` / `refundToken` (low-level ERC-20 `call`), and `refundNative` (`call{value:}`) all follow checks-effects-interactions: state (`releasedForTranche`, `releasedNative`, `refundedNative`, `donorToken`, `raisedToken`, etc.) is written BEFORE the external call. A reentrant callback therefore sees already-updated counters and cannot double-spend a refund or re-release a tranche. No classic reentrancy was found.
- Residual exposure: a malicious allowlisted token (admittable only by the authority) could reenter from within `_safeTransfer`/`_safeTransferFrom`, but because effects precede interactions, the impact is limited to cross-function reentry that still respects the (currently insufficient, see findings 1/3) ceilings. Adding `releasedToken[token] <= raisedToken[token]` (finding 1) and a `nonReentrant` guard on the release/refund/donate token paths would close this defensively. A `ReentrancyGuard` is recommended as cheap insurance even though no exploitable path was found today.
- Per-campaign isolation holds: each `CampaignEscrow` is a distinct deployed contract holding only its own campaign's ETH and tokens, so funds cannot commingle across campaigns. This invariant is sound.

## Improvement recommendations

1. **Bound release by funds raised, per asset.** Add `releasedNative + amount <= raisedNative` and `releasedToken[token] + amount <= raisedToken[token]`, and cap the cumulative `approved` per asset at `raised` in `recordProof` (findings 1, 8). This is the single most important fix and the EVM mirror of the Solana release-ceiling remediation.
2. **Make proofs write-once.** Reject re-recording a `(tranche, asset)` that already has a non-zero `approved` / `proofHash`, and add a monotonic tranche counter; reject `amount == 0` (findings 3, 8).
3. **Harden refund math.** Make `_refundable` saturating so a corrupted `released` counter can never brick refunds for all donors (finding 2).
4. **Adopt delta-aware token accounting** (measure `balanceOf` before/after transfer) and keep the allowlist restricted to standard, non-fee tokens with the constraint documented (finding 4).
5. **Enforce separation of duties in code.** Forbid `approver == authority` in both `setApprover` and `setAuthority`, require an explicit distinct approver at construction, and optionally gate release on `approver != authority` (finding 5).
6. **Make the admin/owner a transferable, Safe-compatible, two-step role (the EVM mirror of the Solana `set_admin`).** The `authority`/`approver` roles are already plain `address` values, so a Gnosis Safe multisig can hold them today and rotation already exists via `setAuthority`/`setApprover`. The missing piece is SAFETY: replace the single-step setters with a two-step propose/accept handshake (`pendingAuthority` + `acceptAuthority`, e.g. `Ownable2Step` semantics) so a mistyped or non-controllable address cannot brick the protocol, and the incoming Safe must prove control by calling `accept*` (finding 6). Emit events on both propose and accept. This satisfies the requirement that the owner be a transferable, Safe-compatible role and closes the one-call-brick risk.
7. **Restrict release redirection.** Reject `to == address(this)` (and consider binding `to` to the proof) so release cannot burn approved headroom into a no-op (finding 7).
8. **Add a `ReentrancyGuard`** to `donateToken`, `releaseToken`, `releaseNative`, `refundToken`, and `refundNative` as defense-in-depth, even though no live reentrancy was found.
9. **Run Slither + Aderyn in Docker** (`chain/docker/`, Foundry stable) and require zero new findings before any deploy, and add Foundry negative tests for each finding above (over-release beyond raised, refund-underflow DoS, proof re-record raising the ceiling, self-directed release, single-key role collapse). Keep coverage at the project's 95% floor.
