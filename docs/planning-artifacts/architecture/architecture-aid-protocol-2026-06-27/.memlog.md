- (decision) AD-11 X OAuth person-identity, server-side only, never a financial authority. Binds: all non-wallet identity (testers, requester public-identity link, donor Twitter aggregation). Prevents: X tokens/secrets reaching the browser; conflating signed-in-with-X with money authority; a second auth path that can move funds. Rule: X OAuth 2.0 + PKCE runs entirely in a Worker; client secret and access tokens never reach the client; sessions are HttpOnly cookies backed by KV with short TTL. X is an attestation and contact signal only; wallet-signature auth authorizes money writes and AD-2 keeps on-chain authoritative. X does not return email; any email is user-supplied and validated separately.
- (decision) AD-12 Telegram is the community comms and notification channel, linked by one-time deep-link token, never a financial authority. Binds: tester/ambassador/requester comms, 2FA, proof reminders. Prevents: an unverified chat acting for someone; the bot becoming an auth or money path; webhook spoofing. Rule: the bot webhook is verified by a secret-token header; a chat links to a verified identity only via a single-use short-TTL deep-link token (start <token>) minted inside that identitys authenticated session; 2FA codes are hashed, single-use, TTL-bounded. Telegram is contact, notification, and step-up only; it never authorizes fund movement (AD-2/AD-4 unchanged).
- (decision) AD-13 Growth and trust surface (tester whitelist, ambassadors) sits off the money-critical path; eligibility uses public-identity signals; rewards never bypass escrow or proof. Binds: tester whitelist, ambassador program, eligibility scoring. Prevents: growth incentives becoming a backdoor around escrow/verification; sybil or bot testers; treating reward payouts as campaign funds. Rule: eligibility gates on public-identity signals (account age, real-follower floor, follow, non-disposable email) consistent with AD-5 tiers, validated via a public-data adapter (RapidAPI); tester/ambassador rewards are capped, manual, paid out-of-band, and never relax AD-3/AD-4/AD-7; eligibility data lives in D1 as a rebuildable projection, never an authority over money.
- (decision) AD-14 Two-Worker edge topology over shared D1 and KV; the projection rule (AD-2) holds across both. Binds: edge deployment, data ownership. Prevents: divergent data authorities between the two Workers; either Worker becoming a money authority; routing or role drift. Rule: the edge runs as two Cloudflare Workers sharing one D1 + KV: the app Worker (product: SPA, canonical API, admin, news cron) and the apex Worker (growth and comms: coming-soon, tester whitelist, Telegram bot, 2FA); both treat D1 as the rebuildable projection; neither is the financial source of truth; cross-Worker shared state goes through D1/KV, never private Worker-to-Worker coupling; run_worker_first guards /api/* so SPA asset-fallback never shadows API routes.
